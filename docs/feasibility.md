# 가능성 검토 — 실데이터 (2026-10-25)

## 목적

합성 문의 20건에 맞춘 루프가 실제 문의 분포에서도 **안전하게(사람 몫은 사람에게)** 도는지, 어디까지 **보조(초안)**가 되는지 숫자로 본다. 품질(문체·정확도)이 아니라 행동(넘김·초안·무시) 일치만 본다.

## 데이터

- 내부 메일 표본: 고객 메시지 → 바로 다음 우리 답장 쌍 996건과 쌍별 라벨(문의유형·우리대응·자동화등급 `auto_ok`/`draft_approve`/`human_only`·CS 범위). 레포 밖 보관, 로컬 mock 실행. 레포에는 스크립트와 집계만 둔다.
- 라벨은 **모델이 붙인 검수 전 초안**이다(반복 템플릿 일괄 부여 포함). 정답이 아니라 기준선으로 읽는다.

## 방법

`LLM_PROVIDER=mock node scripts/eval-real.js [데이터 폴더] [출력 폴더]` — 결정적, 765건 1초 미만. 두 번 돌려 집계가 같음을 확인했다.

1. 조인: 라벨 → 쌍은 (쌍유형, threadId, 문의시각, 답장시각), `행번호`(1부터)로 교차 확인 — 996/996 일치. 평가셋 → 라벨은 (threadId, 문의시각) — 60/60 단일 매치, 라벨 값도 일치.
2. 채널: 플랫폼 이용·크리에이터/채널 측 → `support`, 온보딩·도입 → `onboarding`, 광고대행 견적·단가·캠페인 기획 → `sales`. 그 밖(진행 중 캠페인 실무·제휴·협업 제안 등)은 건너뛰고 센다.
3. 쌍마다 새 `:memory:` DB → `cases.addInbound`(`POST /api/inbound`와 같은 서비스 함수, 인용 제거 `stripQuotes` 포함) → `loop.runCycle` → `decisions`의 마지막 `execute`·`triage`·`gate` 기록을 읽는다. 정책 팩은 그대로(L1, 섀도 끔). 발신 주소는 가짜, 폼 값(knownFacts)·스레드 앞 메일은 넣지 않는다.
4. 기대: `human_only` → HANDOFF(안전). `draft_approve`·`auto_ok` → DRAFT 또는 ANSWER_AND_HANDOFF(보조). `human_only`가 DRAFT로 끝나면 **치명 누락**.
5. 안전장치: `LLM_PROVIDER=mock`이 아니면 exit 1, `fetch` 무력화, API 키 환경변수 제거, 출력 폴더가 레포 안이면 exit 1. 행별 결과(본문 없음)는 레포 밖 폴더에만.

## 무엇이 일반화되고 무엇이 안 되나

mock은 합성 20건에 맞춘 키워드 규칙이다. 이 결과는 **루프 구조**의 검증이지 분류 품질의 검증이 아니다.

일반화되는 것
- 코드 경로: 실메일 765건이 예외·중단 없이 끝났다. H 등급·위험 신호 → 넘김, 견적 → 답장+넘김, 미등록 intent → unclear 넘김이 정책대로 돈다. 판단이 결정적이다.
- 단어 하나로 갈리는 신호: "환불"(81건 넘김, 그중 74건 `human_only`), "탈퇴"(125건 초안, 라벨 대부분 `draft_approve`), 반복 폼 템플릿(온보딩 보조율 91.8%).
- 안전 쪽 기본값: 모르면 넘긴다. 보조 대상 179건이 넘김으로 갔지만 그건 비용이지 사고가 아니다.

일반화되지 않는 것
- 분류: 24%가 unclear. 실제 LLM은 이걸 어떤 intent로든 분류한다 — 그러면 지금 "우연히 안전한" 42건이 초안으로 갈 수 있다. **mock의 재현율 60.6%는 실제 LLM 재현율의 상한도 하한도 아니다.**
- 치명 누락 25건은 키워드가 아니라 **의미**(결제 취소 = 환불, 할인 요청, 권한 부여)로 갈린다. 규칙을 더 붙이면 이 표본엔 맞추겠지만 다음 표본에서 또 샌다.
- guard·검수: mock 응대가 KB 문장을 그대로 붙이므로 guard가 한 번도 안 걸렸다. 금액·날짜·약속 차단은 이 실험으로 검증되지 않았다.
- 맥락: 쌍의 71%(540/765)가 스레드 중간 메시지인데 앞 메일 없이 한 통만 넣었다. "그럼 그렇게 진행해 주세요" 같은 메시지는 맥락 없이 판단할 수 없다.
- 라벨: 검수 전 모델 초안이다. 특히 sales 견적 `human_only` 75건과 `draft_approve` 35건의 경계는 사람이 다시 봐야 한다.

### 실제 LLM 실행에 필요한 것

1. **익명화 단계**: 이름·회사명·이메일·전화·URL·주문/결제 식별자를 치환. `guard.maskContacts`는 이메일·전화만 가린다 — 이름·회사명은 폼 필드에서 사전을 만들어 치환하고, 치환 결과를 사람이 표본 검수한다.
2. **승인**: 데이터 소유자 서면 승인, 외부 전송 범위(평가셋 60건만)·보존 정책 확인.
3. **평가셋 60건만** 실행. 스레드 앞 메일(익명화)까지 넣은 판과 한 통만 넣은 판을 둘 다 돌린다. 프롬프트·KB·정책 버전을 결과와 함께 기록.
4. 평가셋 라벨 60건을 사람이 먼저 검수한다(모델 초안 라벨로 모델을 채점하지 않게).

## 판정 — "L0 섀도, 실제 수신"

**조건부 GO.** 섀도는 초안을 승인 큐에 올리지도, 보내지도 않는다 — 치명 누락이 고객에게 닿는 경로가 없고, 이 실험의 목적(라우팅 분포 측정)에 맞다. 조건:

- 미러 전용: 기존 응대와 병행하되 담당자는 대시보드로 응대하지 않는다. `MAIL_PROVIDER=mock`, `NOTIFY_WEBHOOK_URL` 비움(섀도에서도 넘김은 사람 몫으로 기록·알림된다).
- LLM은 mock 또는 위 익명화·승인을 거친 provider만. mock 섀도 초안은 KB 복사라 품질 평가 가치가 없다 — 라우팅만 본다.
- P1(가능하면 P2) 적용 후 시작.

**L1(승인 큐 노출)은 NO-GO.** 실제 LLM으로 평가셋 60건을 돌려 `human_only` 치명 누락 0건(승격 기준 `maxCritical: 0`)을 확인하기 전에는 support·sales 모두 L1을 켜지 않는다.

### 합성 시나리오 20개 (사람 기준값 없음)

`npm run demo` — 합성 문의 20개가 기대 행동(초안 9 · 넘김 9 · 무시 2)과 20/20 일치했다. 실제 사람 답장이 없어서 위 비교에는 넣지 않았고, 회귀 테스트로만 쓴다.

### 이 수치를 읽을 때

1. **mock LLM이다.** 분류가 키워드 기반이라 일치율 75%·재현율 70.2%는 mock 기준이다. CS 행의 23%(178/765)가 `unclear`·낮은 확신 넘김인데, human_only 라벨에서는 이게 우연히 "일치"로 잡힌다.
2. **속도 비교가 아니다.** 에이전트 ms는 코드만 잰 값이다(LLM 지연·승인 대기·발송 제외). 사람 시간은 밤·주말·대기를 포함한 벽시계 시간이다(27%가 24시간 넘음). 두 값을 "N배 빠르다"로 묶지 않는다. 고객 첫 응답까지의 에이전트 모드 시간은 승인 대기를 재야 나온다(섀도·L1 운영 지표).
3. **라벨은 모델이 붙인 검수 전 초안이다**(data README). 일치·치명 모두 라벨에 기대고, 치명 4건 중 일부는 같은 본문이 다른 등급을 받은 라벨 불일치다(위 「결과」).
4. **메일 한 통만 본다.** 쌍의 71%가 스레드 중간인데 쌍마다 새 DB로 돌렸다. 실제 루프는 앞 대화를 맥락으로 본다.
5. **금액·날짜 0%는 성향이 아니라 차단이다.** guard가 초안에서 막으므로 0%가 정의상 나온다. 사람 쪽 15%·26%는 "에이전트가 대신 말할 수 없어 사람에게 넘겨야 하는 몫"의 크기로 읽는다.
6. **감사 인사 시나리오(S20·S21·S27·S30·S45)의 일치율은 의미가 없다.** 보조 라벨은 초안을 기대하는데, 감사 인사에는 답하지 않는 것도 맞는 행동이다.
7. **작은 그룹.** 채널이 있어 실제로 돈 시나리오 중 n≥10은 14개(S01–S04·S06–S12·S14–S16)다. 나머지 시나리오의 비율은 참고로만 본다.
8. **문장 품질은 비교하지 않았다.** mock 초안은 KB 문장 복사라서 사람 답장과의 품질 비교는 실제 LLM(B-M2) 뒤에 한다.


## L2 자동 발송 + 1차 응대 (2026-10-27 2차)

**결정 (2026-10-27).** "L2 바로 켬", 목표는 에이전트 1차 응대율 80% 이상이다. 응대는 세 가지로 나눈다.

- **완전 자동응대:** 승인 없이 자동 발송하고, 사람 손이 가지 않는다.
- **사람에게 넘김:** 에이전트가 접수 안내와 질문 요약 브리핑을 남기거나, 답장+넘김을 하거나, 승인 대기 초안을 남긴다.
- **응대 못함:** 나간 답도 초안도 없다.

**바꾼 것** — 코드·테스트 기준은 `docs/deployment.md` §5와 `test/l2-ack.test.js`다.

- **L2 허용 intent는 6개다.** support 탈퇴·영수증·구독 해지, onboarding 온보딩 신청·미팅, sales 서비스 질문.
  - 고른 기준: 위 L1 평가에서 초안을 냈는데 사람 몫 라벨이 0건인 intent.
  - 예외 1 — 온보딩 신청: 사람 몫 1건이 있다. 이 1건은 같은 신청 폼 156건과 라벨이 갈린 라벨 불일치다. 빼면 즉시 응대율이 66%로 떨어져서 L2에 남겼다.
  - 예외 2 — sales 검토 중(`reviewing`): 아래 전체 실행에서 사람 몫 1건이 자동 발송돼서 L1로 내렸다.
- **자동 발송 경로는 따로 만들지 않았다.** 사람 승인과 같은 `approveDraft`를 탄다(선점 → 재확인 → guard 재검사 → 멱등키). 막히면 초안은 승인 대기로 남는다.
- **넘김에는 접수 안내를 보낸다.** 팩 템플릿(`ackReply`)으로, 사실·날짜를 담지 않는다. 지시 변경 시도·법적 언급·보낸 사람이 바뀐 회신은 보내지 않는다. 케이스당 한 번이고, 질문 요약은 Briefer 브리핑으로 담당자에게 간다.
- **`AUTO_SEND=0`은 kill switch다.** 둘 다 끈다.
- **평가 범위를 넓혔다.** 위 L1 평가에서 SKIP이던 진행 중 캠페인 실무·제휴 제안 81건을 영업 수신함(sales)으로 들어온다고 **가정**해 함께 돌렸다. 그래서 실행 846건이다(빈 본문 1건만 제외).

### 읽을 때

1. 위 「시나리오 태스크」 절의 캐비엇 1–8이 그대로 적용된다. mock LLM, 라벨 미검수, 메일 한 통 맥락, 속도 비교 아님.
2. **"종결"은 관측하지 않았다.** 대리 지표(사람 답 뒤 재문의율)는 사람 답장 기준이다. 에이전트 자동 답 뒤에 실제로 종결되는지는 L2 운영에서 재야 한다.
3. **가정 라우팅 81건은 수신함을 추정한 결과다.** 실제 수신 주소로 채널을 정하면 바뀔 수 있다.
4. **실제 LLM 평가(B-M2) 전에 L2를 켰다.** 자동 발송된 사람 몫이 1건이라도 나오면 `AUTO_SEND=0`으로 끈다(`docs/deployment.md` §5).
